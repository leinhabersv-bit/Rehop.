# 01 — Executive decision sheet

## The project in one sentence

**RideRescue monitors a booked ride's probability of pickup failure, prepares alternatives before a no-show, and safely recovers from confirmed cancellations until pickup is verified or a user-defined limit is reached.**

**Tagline:** *Your cab cancelled. Your plans shouldn't.*

**Binding amendment:** Read [PRE-FREEZE v1.1](../design-freeze-v1.1.md) first. It overrides older language in any sections below.

## Why this product exists

A rider may receive an accepted booking while the driver stays stationary, travels away, repeatedly increases the ETA, or cancels. The rider then manually checks several apps and repeats the process. Comparison apps help pick a cab **before** booking; RideRescue focuses on the **failure-prone interval between driver acceptance and actual pickup**.

## What the hackathon build will actually prove

| We WILL demonstrate | We will NOT claim |
|---|---|
| A running frontend connected to a real backend | Real access to commercial cab-provider systems |
| Four independently simulated provider adapters, visibly labeled | Actual Provider A–D driver positions or quotes |
| Time-based movement and ETA streams | Evidence that our synthetic model performs on real rides |
| Pickup-risk estimates based on observable signals | Certainty about a driver's intent or misconduct |
| Alternative discovery and bounded rebooking | Guaranteed pickup or guaranteed arrival at destination |
| Safety against duplicate active rides and surprise fares | Automatic payment, unauthorized app control, or hidden cancellation fees |
| An evaluation harness with reproducible scenarios | Claims of real consumer money/time saved from simulated tests |

**Non-negotiable product rule:** success means **pickup confirmed**, not “booking confirmed.”

## The one demo moment to optimize

A simulated Provider A ride is accepted; the driver barely progresses and ETA rises; the agent detects pickup risk and finds a backup; the original booking is cancelled **with confirmation**; Provider B is booked; Provider B cancels; RideRescue uses the user's pre-approved rules to book Provider C; pickup is confirmed; the agent stops. A second demo must show **a traffic delay that clears**, where the agent correctly **does not** cancel or double-book.

## Definition of a credible submission

- A new evaluator can clone and run the system with one documented command sequence.
- Every scenario is generated by backend state and events, not a pre-scripted frontend animation.
- The team runs automated tests and publishes actual measurements with their assumptions.
- All neutral simulated providers and data are clearly labeled in the UI, video and README.
- The repository, setup documentation and short demo video meet event submission requirements.

# 02 — Scope and acceptance criteria

## Primary persona

An urban commuter with an appointment, train, class or flight who values **reliable pickup** over purely the lowest fare. The initial demonstration is set in Chennai, with predefined fictionalised/illustrative ride data; no real driver's data is collected.

## MVP user stories — must ship

| ID | User story | Observable acceptance criterion |
|---|---|---|
| U01 | As a rider, I can choose pickup and destination. | A journey is created with two valid predefined locations and a request timestamp. |
| U02 | I can set cost and recovery constraints. | User chooses INR price ceiling, max recovery attempts, and whether automatic rebooking after confirmed cancellation is allowed. |
| U03 | I can view simulated quotes. | Quotes from four provider simulators show ETA and fare, marked *simulated*. |
| U04 | I can book one initial simulated ride. | Backend creates one active ride and starts emitting ordered events. |
| U05 | I can see whether my driver is making progress. | UI updates driver distance, ETA, freshness, and risk explanation from backend events. |
| U06 | I get an early warning when pickup is at risk. | Stalled-progress scenario emits a risk warning before or around cancellation; warning shows contributing signals. |
| U07 | I see an alternative, not merely an alert. | A safe candidate within policy is found, or an explicit “no suitable backup” state appears. |
| U08 | I control risky preemptive changes. | No cancellation or second active booking occurs merely because risk is high; switching requires user approval. |
| U09 | I recover from confirmed driver cancellation. | If the user opted in, the engine books a replacement subject to cap/attempt/availability checks. |
| U10 | A second cancellation can trigger another bounded retry. | Replacement cancellation is handled using the same state machine, without infinite retry loops. |
| U11 | I can know that recovery is finished. | ARRIVED/boarding confirmation stops searching and auto-actions; no later recovery fires. |
| U12 | The team can prove robustness. | Reproducible scenarios, tests, metrics and failure cases appear in an evaluation report. |

## Explicitly OUT of scope for this hackathon

Real bookings, live provider tracking, card/UPI payments, real cancellation fees, reverse engineering mobile apps, scraping protected ride apps, account linking to providers, live geolocation permission, voice recognition, production user accounts, predictive model trained on real users, and completion of the entire road journey after boarding.

**Optional polish only after all must-ships pass:** voice *input* for pickup/destination, browser map tiles, multilingual microcopy, downloadable incident timeline, reusable trip presets.

## Product behaviors that must never occur

1. Two active paid/accepted cab bookings by default.
2. Cancellation of an active ride because of a single delayed GPS tick.
3. Auto-booking above the user's declared INR ceiling.
4. Endless recovery loops or attempts after user cancellation/boarding.
5. Displaying “the driver is cheating” or alleging intent from movement data.
6. Hiding that the entire ecosystem is simulated.
7. Pretending an API call succeeded when it timed out or returned an ambiguous result.

# 04 — Immutable v1 domain model

Treat these as the design intent. The authoritative machine-readable versions live in `contracts/openapi.yaml` and `contracts/events.schema.json`; freeze those by the end of Day 2.

## Enumerations

**Provider:** `PROVIDER_A`, `PROVIDER_B`, `PROVIDER_C`, `PROVIDER_D`.

**Ride state:** `SEARCHING`, `CONFIRMED`, `DRIVER_EN_ROUTE`, `DRIVER_ARRIVED`, `IN_PROGRESS`, `COMPLETED`, `DRIVER_CANCELLED`, `RIDER_CANCELLED`, `FAILED`.

## Non-negotiable invariants

- At most **one** ride may be in `CONFIRMED`, `DRIVER_EN_ROUTE`, `DRIVER_ARRIVED` or `IN_PROGRESS` per journey. Enforce on the backend, not just visually.
- `active_ride_id` is changed only after an adapter operation has a **confirmed** result.
- Every mutating request is idempotent or supplies `idempotency_key`.
- Every state change increments `journey.version` and appends an event with monotonically increasing `seq`.
- Arrival, boarding, completion or explicit user cancellation stops recovery actions.
- If cancellation status is uncertain, block replacement booking and show “verification required,” rather than risking duplicates.
- An expired quote cannot be booked; request a fresh one.
- A rejection by spending policy is absolute even if a model recommends switching.

# 06 — Simulation engine: required fidelity

A **simulator is not a slideshow**. It maintains a clock, per-driver positions, ride assignments, random seeds, provider delays, candidate availability and action outcomes. The backend produces a new event each time simulation state actually changes.

## Engine details

- Fixed logical tick: **5 simulated seconds** (UI may run at 5x–20x playback speed for demo).
- Deterministic pseudorandom generator with user-provided seed. Same scenario + seed + policy produces the same event history.
- Each provider has a distinct quote and failure profile **in the simulation only**. These are invented, not actual provider performance statistics.
- A driver has a predefined route toward pickup and a time-varying motion profile: movement, stationary period, GPS jitter or cancellation.
- ETA is recomputed from simulated progress and a traffic multiplier, not arbitrarily animated on the client.
- A `quote_id` expires and a booking can fail independently of receiving the quote.
- Use a simulated local route canvas; optionally show street-like geometry, but never call it a live map.

## Minimum scenario catalogue

| ID | Required scenario | Expected behavior |
|---|---|---|
| S01 | Healthy pickup | No rescue, driver arrives, rider boards. |
| S02 | Temporary traffic stop, then movement | Risk may rise briefly; **no unnecessary cancellation**. |
| S03 | Driver stalls and ETA rises persistently | Alert + backup discovery; approval requested for preemptive switch. |
| S04 | Sudden driver cancellation | Auto-rebook only if opted in and policy passes. |
| S05 | Replacement driver also cancels | Second attempt works; retry count respected. |
| S06 | All backups unavailable | Clear recovery-exhausted state; no phantom success. |
| S07 | Available backup exceeds fare cap | Reject candidate; no over-budget booking. |
| S08 | Stale GPS/telemetry | Risk becomes `UNKNOWN` or low confidence; don't falsely accuse. |
| S09 | Driver stopped near pickup/traffic signal | Arrival/proximity handling avoids unnecessary switching. |
| S10 | Cancellation and arrival events race | Exactly one authoritative terminal transition; never double-book. |
| S11 | User cancels during recovery | All queued auto-actions stop and audit trail remains. |
| S12 | Booking API times out with unknown result | No retry that might create a duplicate; reconcile/abstain. |

**Critical edge case:** cancelled by **driver** is different from cancelled by **rider**; the former may qualify for auto-recovery, the latter must always stop the journey.

# 07 — Pickup-risk intelligence (BE2)

## What the model is predicting

**Target:** the likelihood that the currently confirmed ride will *fail to produce a timely pickup within a defined simulation horizon*. It is **not** predicting whether a driver is dishonest. Define `pickup_failure_within_5min` as the evaluation label in simulated time, and keep the horizon explicit in code and UI.

## Feature contract

| Feature | Definition | Failure mode to guard against |
|---|---|---|
| `net_progress_m_120s` | Earlier distance to pickup minus current distance over 120 s | Driver may legitimately detour around one-way roads |
| `stationary_duration_s` | Duration with speed under a small threshold | Red lights, pickup queue, congestion |
| `eta_delta_s_120s` | Current ETA minus ETA 120 s ago | ETA refresh can be noisy |
| `distance_to_pickup_m` | Latest simulator distance | Important for avoiding false alerts near pickup |
| `gps_age_s` | Current sim time minus last position timestamp | Stale data is **unknown**, not evidence of stalling |
| `gps_quality` | Simulator-provided signal quality | Poor signal must lower confidence |
| `route_progress_ratio` | Distance reduced divided by distance initially remaining | Avoids bias between short and long pickups |
| `provider_cancel_signal` | Real event from simulated provider | Confirmed cancel is categorical, no model needed |
| `elapsed_since_accept_s` | Booking age | Avoid flagging normal first-minute delay |

**Baseline first:** implement an interpretable rule score (e.g. sustained low net progress **and** increasing ETA with fresh GPS, at a meaningful distance). Then, only if time permits, fit a small scikit-learn classifier on training simulation seeds; calibrate and compare it against the baseline on **held-out seeds and scenario variants**.

The risk engine emits a 0–100 score, a `LOW/MEDIUM/HIGH/UNKNOWN` band, confidence, and concise signal codes. For demo purposes suggested initial bands are low 0–39, medium 40–69, high 70–100; calibrate during evaluation and document changes. **Do not claim a synthetic-model probability is real-world calibrated.**

## Decision policy: model advises, policy decides

```python
if journey.state in STOPPED_OR_PICKED_UP:
    decision = STOP
elif ride.state == DRIVER_CANCELLED:
    decision = REBOOK_AFTER_CANCEL if policy.opted_in else REQUEST_APPROVAL
elif telemetry_is_stale_or_unreliable:
    decision = MONITOR  # show uncertainty; no auto-cancel
elif risk_band == HIGH and safe_backup_is_available:
    decision = REQUEST_APPROVAL  # preemptive switching requires consent
elif risk_band in (MEDIUM, HIGH):
    decision = SEARCH_BACKUP  # searching does not create a ride
else:
    decision = MONITOR
```

**Operational principle:** driver movement/risk detection can trigger **parallel quote searches**, not parallel active bookings. The original ride must be verified cancelled before another is booked, unless the user explicitly approves a separate future production feature that tolerates overlapping rides. That overlapping feature is **not part of MVP**.

## Explainability rules

Good: “The driver made little net progress in the last 3 simulated minutes while the ETA rose by 5 minutes.”

Bad: “Driver is scamming you,” “Driver will definitely cancel,” or “100% no-show.”

Every visible risk explanation must be reconstructible from logged feature values. If an LLM creates the sentence, validate its numerical statements against the structured assessment.

# 08 — Recovery state machine and safety policy (BE2)

## Recovery types

**A. Before any cancellation (proactive):** locate alternatives in parallel; alert the rider; show the consequences. Switch only after rider approval and confirmation that the original simulated booking is cancelled.

**B. After confirmed driver cancellation (reactive):** if the user opted in before the ride, the agent may book a replacement within fare/attempt limits. If not opted in, show one-tap approval and do nothing until approved.

## Exact safe-switch transaction

1. Re-fetch authoritative journey + active ride + quote freshness.
2. Verify journey is not terminal and `expected_version` still matches.
3. **Refresh a backup quote immediately before cancellation** (`search` + `select` + `init`); verify fare, expiry, attempt count, fee cap and eligibility. If unavailable, retain the original ride.
4. Display a conditional possible rider-cancellation fee: under MoRTH MVAG 2025 clause 18.2, 10% of fare up to Rs100 only when cancelling without a valid reason; this is an illustrative bound, not an actual provider quote. Require approval, then request cancellation if original ride remains active.
5. Wait for explicit `RIDE_CANCEL_CONFIRMED` (or authoritative terminal state); if uncertain, **stop**.
6. Generate a stable idempotency key for replacement booking.
7. Attempt one booking through a BE1 provider adapter.
8. Reconcile the provider response: confirmed success, confirmed failure, or unknown; never interpret unknown as failed-safe to retry.
9. Persist event, attempt count, assigned ride and journey version atomically.
10. Report success or a precise block reason. Resume monitoring the replacement if confirmed.

## Recovery budget and guardrails

- `max_recovery_attempts` counts **replacement booking attempts**, not search requests. Default **2** for the demo.
- `max_total_fare_inr` applies to the **new ride's quoted fare**; show potential simulated cancellation fees separately if known. Never silently add fees.
- Prefer ETA improvement over a small fare difference; actual ranking formula is a logged simulation policy, not an industry benchmark.
- Don't retry the same provider immediately if its booking just failed; a small simulated cooldown protects against loops.
- A received `DRIVER_ARRIVED`, `PICKUP_CONFIRMED`, `USER_CANCELLED` or `EXHAUSTED` event stops all pending action jobs.
- Expose user-visible controls: **Keep current ride**, **Switch to backup**, **Stop all recovery**.

## Ranking a backup (first version)

Use `need_by` (latest acceptable pickup) to compare predicted lateness when waiting versus switching, including possible cancellation fee and fare difference. A low-urgency ride must not automatically be switched just because it is stationary.

Use hard filters before scoring: within price cap, quote not expired, provider able to book, and valid pickup ETA. Rank allowed candidates by weighted normalized ETA and fare, with a small deterministic reliability prior **based only on simulator settings**. Do not call it a real provider reliability ranking.

**Rescue cannot guarantee a ride.** If no candidate qualifies, the correct result is `RECOVERY_BLOCKED` or `RECOVERY_EXHAUSTED` with a clear reason.

## Mobile-first design rules

- Design for a 390px phone viewport first; full desktop layout afterward.
- Fixed, always-visible label: **“SIMULATED DEMO — no actual cab will be booked.”**
- Limit the primary action to one at a time. Don't have “Cancel” and “Switch” buttons with the same emphasis.
- Never show a backup as *booked* until backend `RECOVERY_SUCCEEDED` confirms it.
- Indicate telemetry freshness: “updated 5 simulated seconds ago.” If stale, show `Location unavailable`, not a frozen live position.
- Use text + icon + color for risk; don't rely only on red/green.
- Keyboard accessible buttons, focused dialogs, accessible timeline labels, and respectful reduced-motion behavior.
- No actual provider logos required; use neutral labels like “Provider A (simulated)”.
- On WebSocket reconnect, fetch REST snapshot, then replay events after `last_event_seq`; deduplicate events by `event_id` or `seq`.

**Do not hard-code a happy path.** Every error state must have an honest explanation and an available safe action.

## Minimum measurable metrics

| Metric | Exact definition | Target / use |
|---|---|---|
| `pickup_success_rate` | Fraction of simulated journeys ending in `PICKUP_CONFIRMED` | Compare to no-rescue baseline; no fixed claim |
| `time_to_pickup_sec` | Simulation seconds between first booking and confirmed pickup | Compare median and p90 to baseline |
| `time_from_cancel_to_new_booking_sec` | Delay between confirmed cancellation and new confirmed ride | Report median and p90 |
| `false_warning_rate` | Healthy / temporary-traffic cases incorrectly tagged high-risk | Minimize; report transparently |
| `unnecessary_switch_rate` | Rides switched in runs where original would have arrived in time | Especially important safety/usability metric |
| `duplicate_active_booking_count` | Journey snapshots with two active rides | **Must equal 0** |
| `over_cap_booking_count` | Confirmed replacement with fare above cap | **Must equal 0** |
| `post_stop_action_count` | Any auto-action after pickup/user cancel | **Must equal 0** |
| `recovery_exhaustion_handling` | No available/cost-safe backup returns explicit terminal state | 100% expected in fixtures |

## Baselines and experiment design

Run **paired simulations** with identical scenario seeds for: `B0 = no recovery (wait/manual simulated fallback)`, `B1 = naïve stationary-duration rule`, `B2 = RideRescue risk + recovery policy`. Keep traffic profiles, driver positions and quotes matched where feasible. The model must not see test seeds or future cancellation labels when predicting. Include at least 200 simulated journeys overall; use 500+ if runtime permits, distributed across scenario families.

**Never present an arbitrary simulated manual-response delay as a measured human behavior.** Label every time constant as a benchmark assumption. Report mean/median/p90, counts and adverse outcomes; include scenarios where RideRescue performs worse. A score only on the handcrafted hero scenario is insufficient.
