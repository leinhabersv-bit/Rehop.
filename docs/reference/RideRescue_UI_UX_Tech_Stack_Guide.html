00 / Overview

What this document defines

One source of truth for every text label, screen state, frontend layout and implementation choice.

The project promise

“Your cab cancelled. Your plans shouldn’t.”

RideRescue monitors a simulated driver’s progress, identifies pickup risk, prepares safe alternatives and recovers from confirmed cancellations within rider-approved limits.

In this PDFWho uses itWhat it settles
Product language & screen flowFE1 + FE2Exact copy, actions, tags, empty states and notifications
Design system & layoutsFE1 + FE2Colors, typography, spacing, mobile/desktop rules
Technology & architectureAll fourChosen stack, modules, API/event integration
Ownership & QAAll fourNo overlapping code ownership, deliverables, launch tests

Non-negotiable product truth

This hackathon product operates four mock providers and never books a real cab. Every fare, ETA, driver position, and provider name must be labelled simulated. Do not present generated results as live Provider A–D data.

Definition of success

A ride is not complete when the provider accepts it. The experience ends only when pickup is confirmed, the rider stops the journey, recovery is blocked, or retry limits are exhausted.

03 / System design

Architecture & project layout

A contract-first monorepo, with simulation and risk/recovery separated by an explicit interface.

Frontend pair

apps/web

FE1: shell, setup, quotes, initial booking, typed client.
FE2: live journey, risk, recovery controls, simulator view.

Backend pair

services/api

BE1: provider adapters, time engine, API, persistence, event feed.
BE2: feature extraction, risk assessment, recovery policy, benchmarks.
